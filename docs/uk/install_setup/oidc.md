# OIDC Аутентифікація

Gramps Web підтримує аутентифікацію OpenID Connect (OIDC), що дозволяє користувачам входити в систему, використовуючи зовнішніх постачальників ідентичності. Це включає вбудовані постачальники Google та Microsoft, а також кастомні OIDC постачальники, такі як Keycloak, Authentik та Authelia.

!!! warning "GitHub як OIDC постачальник більше не підтримується"
    Якщо у вас встановлені `OIDC_GITHUB_CLIENT_ID` / `OIDC_GITHUB_CLIENT_SECRET` з попередньої версії, видаліть їх – вони тепер ігноруються, а користувачі, які раніше входили через GitHub, більше не можуть увійти таким чином. GitHub є постачальником OAuth 2.0, а не постачальником OpenID Connect, і ніколи не повертав заяву, на яку покладається Gramps Web для ідентифікації, тому він ніколи не був повністю надійним.

## Огляд

Аутентифікація OIDC дозволяє вам:

- Використовувати зовнішніх постачальників ідентичності для аутентифікації користувачів
- Підтримувати кілька постачальників аутентифікації одночасно
- Відображати OIDC групи/ролі на ролі користувачів Gramps Web
- Реалізувати єдину аутентифікацію (SSO) та єдине вихід
- За бажанням відключити локальну аутентифікацію за допомогою імені користувача/пароля

## Налаштування

Щоб увімкнути аутентифікацію OIDC, вам потрібно налаштувати відповідні параметри у вашому конфігураційному файлі Gramps Web або змінних середовища. Дивіться сторінку [Конфігурація сервера](configuration.md#settings-for-oidc-authentication) для повного списку доступних налаштувань OIDC.

!!! info
    При використанні змінних середовища не забудьте префіксувати кожну назву налаштування `GRAMPSWEB_` (наприклад, `GRAMPSWEB_OIDC_ENABLED`). Дивіться [Конфігураційний файл проти змінних середовища](configuration.md#configuration-file-vs-environment-variables) для деталей.

### Вбудовані постачальники

Gramps Web має вбудовану підтримку популярних постачальників ідентичності. Щоб їх використовувати, вам потрібно лише надати ідентифікатор клієнта та секрет клієнта:

- **Google**: `OIDC_GOOGLE_CLIENT_ID` та `OIDC_GOOGLE_CLIENT_SECRET`
- **Microsoft**: `OIDC_MICROSOFT_CLIENT_ID` та `OIDC_MICROSOFT_CLIENT_SECRET`

Ви можете налаштувати кілька постачальників одночасно. Система автоматично виявить, які постачальники доступні на основі значень конфігурації.

!!! tip "Microsoft: одно-орендні розгортання"
    Вбудований постачальник Microsoft використовує багатокористувацьку точку доступу `/common` і за замовчуванням приймає входи з будь-якого облікового запису Microsoft. Якщо ви хочете дозволити користувачам входити лише з вашого власного орендаря, використовуйте [кастомний OIDC постачальник](#custom-oidc-providers) з URL-адресою специфічного для вашого орендаря видавця, що підтримує валідацію видавця та обмежує входи до цього орендаря.

### Кастомні OIDC постачальники

Для кастомних OIDC постачальників (таких як Keycloak, Authentik, Authelia або одно-орендний Microsoft Entra) використовуйте ці налаштування:

Ключ | Опис
----|-------------
`OIDC_ENABLED` | Логічне значення, чи увімкнена аутентифікація OIDC. Встановіть на `True`.
`OIDC_ISSUER` | URL-адреса видавця вашого постачальника. Виявлення отримується з `<issuer>/.well-known/openid-configuration`.
`OIDC_CLIENT_ID` | Ідентифікатор клієнта для вашого OIDC постачальника
`OIDC_CLIENT_SECRET` | Секрет клієнта для вашого OIDC постачальника
`OIDC_NAME` | Кастомна назва відображення (необов'язково, за замовчуванням "OIDC")
`OIDC_SCOPES` | OAuth обсяги (необов'язково, за замовчуванням "openid email profile")
`OIDC_USERNAME_CLAIM` | Заява, що використовується для генерації імені користувача (необов'язково, за замовчуванням "preferred_username")
`OIDC_PKCE` | Чи використовувати PKCE, див. [PKCE](#pkce) (необов'язково, автоматично увімкнено, якщо постачальник його підтримує)

### PKCE

З моменту Gramps Web API 3.23, Gramps Web підтримує [PKCE](https://datatracker.ietf.org/doc/html/rfc7636) (Proof Key for Code Exchange, метод `S256`) для потоку авторизаційного коду. Деякі постачальники ідентичності, такі як Pocket ID, можуть бути налаштовані на *вимогу* PKCE для клієнта і відмовляти у вході, якщо його не використовують. Старі версії Gramps Web API ніколи не використовують PKCE, тому входи з таким клієнтом зазнають невдачі.

Чи використовується PKCE, вирішується під час входу наступним чином:

- Якщо `OIDC_PKCE` встановлено на `True`, використовується PKCE.
- Якщо `OIDC_PKCE` встановлено на `False`, PKCE не використовується, навіть якщо постачальник його підтримує.
- Якщо `OIDC_PKCE` не встановлено або встановлено, але порожнє, PKCE використовується, якщо документ виявлення постачальника (`/.well-known/openid-configuration`) містить `S256` у `code_challenge_methods_supported`, і не використовується в іншому випадку.

Для більшості налаштувань вам не потрібно нічого встановлювати. Встановіть `OIDC_PKCE` на `True`, якщо ваш постачальник вимагає PKCE, але не рекламує `S256` у своєму документі виявлення, і на `False`, якщо ваш постачальник рекламує `S256`, але неправильно його обробляє. Як змінні середовища, логічні значення повинні бути написані малими літерами (`GRAMPSWEB_OIDC_PKCE=true`), див. [Конфігурація](configuration.md).

Для вбудованих постачальників відповідні параметри – це `OIDC_GOOGLE_PKCE` та `OIDC_MICROSOFT_PKCE`.

Код перевірки PKCE зберігається в сеансі користувача між перенаправленням до постачальника та зворотним викликом, тому це не вимагає змін у URL-адресах перенаправлення.

### Налаштування з кількома деревами

На сервері з кількома деревами дерево, в яке користувач входить, повинно бути відомим до того, як Gramps Web перенаправляє до постачальника ідентичності, тому вхід починається з:

```
GET /api/oidc/login/?provider=<id>&tree=<tree_id>
```

`tree` є обов'язковим у налаштуваннях з кількома деревами; пропуск його або передача ID дерева, якого не існує, призводить до невдачі входу. На сервері з одним деревом `tree` є необов'язковим, але якщо він наданий, він повинен відповідати налаштованому `TREE`.

Ідентичність OIDC прив'язується до точно одного облікового запису Gramps Web, який, у свою чергу, належить точно одному дереву – вхід у інше дерево зазнає невдачі, а не переміщує обліковий запис. Немає способу зв'язати одну ідентичність у постачальника з обліковими записами в кількох деревах; користувачі, які потребують доступу до кількох дерев, повинні мати окремі ідентичності у постачальника (наприклад, різні імена користувачів або облікові записи).

!!! warning
    Обліковий запис адміністратора сайту без асоційованого дерева (див. [створення адміністративного облікового запису](../administration/owner.md)) не може увійти через OIDC, оскільки вхід OIDC завжди вимагає дерева. Такі облікові записи повинні бути створені та автентифіковані за допомогою локального імені користувача/пароля.

## Обов'язкові URL-адреси перенаправлення

При налаштуванні вашого OIDC постачальника ви повинні зареєструвати наступну URL-адресу перенаправлення:

**Для OIDC постачальників, які підтримують шаблони: (наприклад, Authentik)**

- `https://your-gramps-backend.com/api/oidc/callback/*`

Де `*` є шаблоном regex. В залежності від інтерпретатора regex вашого постачальника це також може бути `.*` або подібне.
Переконайтеся, що regex увімкнено, якщо ваш постачальник цього вимагає (наприклад, Authentik).

**Для OIDC постачальників, які не підтримують шаблони: (наприклад, Authelia)**

- `https://your-gramps-backend.com/api/oidc/callback/custom`

Дерево ніколи не є частиною URL-адреси перенаправлення, навіть на серверах з кількома деревами – воно передається окремо в сеансі, оскільки постачальники вимагають, щоб URL-адреса перенаправлення точно відповідала зареєстрованій.

## Відображення ролей

Gramps Web може автоматично відображати OIDC групи або ролі з вашого постачальника ідентичності на ролі користувачів Gramps Web. Це дозволяє вам централізовано керувати дозволами користувачів у вашому постачальнику ідентичності. Відображення ролей працює однаково для всіх постачальників, вбудованих або кастомних.

### Налаштування

Використовуйте ці налаштування для конфігурації відображення ролей:

Ключ | Опис
----|-------------
`OIDC_ROLE_CLAIM` | Назва заяви в OIDC токені, що містить групи/ролі користувача. За замовчуванням "groups". Підтримуються крапкові шляхи, наприклад, `realm_access.roles`.
`OIDC_GROUP_ADMIN` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Admin" Gramps
`OIDC_GROUP_OWNER` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Owner" Gramps
`OIDC_GROUP_EDITOR` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Editor" Gramps
`OIDC_GROUP_CONTRIBUTOR` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Contributor" Gramps
`OIDC_GROUP_MEMBER` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Member" Gramps
`OIDC_GROUP_GUEST` | Назва групи/ролі з вашого OIDC постачальника, яка відображається на роль "Guest" Gramps

### Поведінка відображення ролей

Якщо жодне налаштування `OIDC_GROUP_*` не налаштовано, відображення ролей вимкнено, і ролі керуються вручну в Gramps Web; нові OIDC облікові записи тоді створюються з вимкненими правами і потребують схвалення існуючим власником або адміністратором (див. [Перший вхід та початкове налаштування](#first-login-and-bootstrapping) нижче).

Якщо відображення ролей налаштовано, при кожному вході:

- Якщо заява про роль присутня і користувач належить до відображеної групи, їм надається відповідна роль.
- Якщо заява про роль присутня, але користувач не належить до жодної відображеної групи, їхня роль встановлюється на вимкнену. Це є стандартним значенням за замовчуванням, а не помилкою – Gramps Web не може вивести роль для групи, яку не розпізнає.
- Якщо заява про роль зовсім відсутня в токені, існуюча роль залишається незмінною; новий обліковий запис все ще за замовчуванням вимкнений.

!!! warning "Google не надсилає заяву про групи"
    Токени Google ніколи не містять заяву `groups`, тому з увімкненим відображенням ролей, входи Google підпадають під "заява відсутня" вище: існуючі користувачі зберігають свою роль, але нові користувачі Google створюються вимкненими і потребують ручного схвалення. Майте це на увазі перед увімкненням відображення ролей лише для іншого постачальника – це не відключає існуючих користувачів Google.

Microsoft Entra повертає ролі додатків і членства в групах лише в ID токені, а не з кінцевої точки userinfo. Gramps Web об'єднує заяви ID токена у відповідь userinfo, щоб `OIDC_ROLE_CLAIM` працював так само, як для інших постачальників; де обидва містять заяву, значення userinfo має перевагу.

## Перший вхід та початкове налаштування

Нові облікові записи, створені через OIDC, починають з вимкненим статусом, якщо відображення ролей не надає їм роль (див. вище). У абсолютно новій інстанції ніхто не може схвалити вимкнений обліковий запис, і якщо `OIDC_DISABLE_LOCAL_AUTH` також увімкнено, немає можливості входу за паролем.

!!! warning "Налаштуйте групу власників/адміністраторів перед першим входом"
    Перед тим, як хтось увійде через OIDC вперше, налаштуйте `OIDC_GROUP_OWNER` (або `OIDC_GROUP_ADMIN`) і переконайтеся, що перший користувач належить до цієї групи у постачальника. В іншому випадку інстанцію не можна буде налаштувати через OIDC.

## Облікові записи та імена користувачів

Облікові записи, створені через OIDC, отримують згенероване ім'я користувача, яке призначається один раз під час створення облікового запису і ніколи не змінюється при подальших входах:

- Вбудовані постачальники: `<provider>_<claim value>`, наприклад, `microsoft_alice@contoso.com`
- Кастомний постачальник: просте значення заяви, наприклад, `alice`

Числовий суфікс додається при конфлікті. Немає способу перейменувати ім'я користувача облікового запису, створеного через OIDC, пізніше; повне ім'я та електронна адреса, навпаки, оновлюються при кожному вході.

Вхід OIDC ніколи не прив'язується до існуючого локального облікового запису, який випадково має таку ж електронну адресу – це навмисно, оскільки зв'язування облікових записів за електронною адресою є вектором захоплення облікового запису. Користувач, який вже має локальний обліковий запис, отримує другий, окремий обліковий запис під час першого входу через OIDC, якщо тільки він спочатку не зв'яже постачальника зі своїм обліковим записом.

З моменту Gramps Web API 3.24, користувачі можуть зв'язувати OIDC ідентичності зі своїм існуючим обліковим записом, а також перераховувати та розривати їх, у [Налаштуваннях користувача > Пов'язані методи входу](../user-guide/settings.md#linked-sign-in-methods). Зв'язування вимагає нещодавнього входу і підтверджується токеном самого користувача, тому це також працює, коли фронтенд знаходиться на іншому походженні, ніж API. Ідентичність може належати лише одному обліковому запису; щоб зв'язати ту, яка вже має свій обліковий запис, адміністратор спочатку видаляє цей обліковий запис (його редагування залишаються, але історія версій більше не показує його ім'я). Останню зв'язану ідентичність можна розірвати лише з поточним паролем облікового запису, і зовсім не можна, якщо `OIDC_DISABLE_LOCAL_AUTH` встановлено.

Електронні адреси від постачальника зберігаються лише в тому випадку, якщо постачальник позначає їх як перевірені (або зовсім не включає заяву `email_verified`); в іншому випадку вхід відбувається без зберігання електронної адреси. Оскільки електронні адреси не повинні бути унікальними (з моменту Gramps Web API 3.22), адреса зберігається, навіть якщо інший обліковий запис вже її використовує.

## Вихід OIDC

Gramps Web підтримує єдине вихід (SSO logout) для OIDC постачальників. `GET /api/oidc/logout/` шукає `end_session_endpoint` постачальника і повертає його як `logout_url` у відповіді; саме фронтенд Gramps Web навігає браузером туди, щоб фактично завершити сеанс у постачальника ідентичності. `logout_url` є `null`, коли у постачальника немає `end_session_endpoint`.

!!! warning "Токени не відкликаються при виході"
    Вихід лише завершує сеанс браузера; наразі немає способу відкликати токен Gramps Web, який вже був виданий. Токени залишаються дійсними до їх закінчення (`JWT_ACCESS_TOKEN_EXPIRES`, за замовчуванням 15 хвилин для токенів доступу), незалежно від того, чи вийшов користувач з Gramps Web або з постачальника ідентичності.

## Виправлення помилок

Почніть з точки, де зупиняється вхід, і дотримуйтесь гілки. Gramps Web записує причину невдалого зворотного виклику (шукайте `OIDC callback error for provider` у журналі сервера), що зазвичай є більш конкретним, ніж повідомлення, показане в браузері.

**1. Чи відсутня кнопка входу?**

- Перевірте `<BASE_URL>/api/oidc/config/`. Якщо `enabled` є `false` або `providers` порожній, OIDC не налаштовано: `OIDC_ENABLED` має бути `True`, а кастомний постачальник потребує як `OIDC_ISSUER`, так і `OIDC_CLIENT_ID`.
- Вбудований постачальник (Google, Microsoft) реєструється лише тоді, коли обидва його ідентифікатор клієнта та секрет клієнта встановлені.
- Перегляньте журнал сервера під час запуску на наявність `Could not load discovery document`. Це означає, що сервер не зміг досягти `<issuer>/.well-known/openid-configuration` (або `OIDC_OPENID_CONFIG_URL`). Він повторно намагається при першому використанні, але контейнер Gramps Web повинен мати можливість розпізнати та досягти URL-адреси видавця самостійно, а не лише ваш браузер.

**2. Чи отримує браузер помилку відразу після відправлення до постачальника?**

Помилка показується постачальником ідентичності, перед тим як ви увійдете.

- *"несумісність URL-адреси перенаправлення"* (або подібне): URL-адреса перенаправлення, зареєстрована у постачальника, повинна точно відповідати, включаючи схему, хост, порт і ID постачальника. Дивіться [Обов'язкові URL-адреси перенаправлення](#required-redirect-uris). Зверніть увагу, що вона формується з `BASE_URL`, тому неправильний `BASE_URL` дає неправильну URL-адресу перенаправлення.
- *Помилка PKCE* (наприклад, `invalid_request`, "вимога коду виклику", або відсутній параметр `code_challenge`): постачальник вимагає PKCE, але Gramps Web його не надіслав. Перейдіть до [гілки PKCE](#pkce-branch) нижче.

**3. Чи приймає постачальник вхід, але Gramps Web потім показує помилку?**

- *`mismatching_state`, або помилка згадує сесію або стан*: браузер не надіслав назад куки сесії, які Gramps Web встановив, коли почався вхід. Цей куки також містить код перевірки PKCE. Переконайтеся, що адреса в браузері відповідає `BASE_URL` (та сама схема та хост), що зворотний проксі передає куки та оригінальний хост, і що вхід починається та завершується в одній і тій же вкладці або вікні браузера.
- *`OIDC authentication failed for <provider>` (HTTP 401)*: перевірте журнал сервера на наявність основної причини. Загальні причини – це неправильний секрет клієнта, URL-адреса видавця, яка не відповідає заяві `iss` токенів, і постачальник, що повертає помилку на зворотний виклик (наприклад, PKCE, див. нижче).
- *Занадто багато спроб*: кінцеві точки входу та зворотного виклику обмежені за швидкістю (5 запитів на хвилину). Почекайте хвилину та спробуйте знову.

**4. Чи успішний вхід, але ви бачите "Обліковий запис на розгляді" або не можете нічого зробити?**

Нові облікові записи створюються вимкненими, якщо відображення ролей не надає їм роль. Дивіться [Перший вхід та початкове налаштування](#first-login-and-bootstrapping) та [Поведінка відображення ролей](#role-mapping-behavior). Адміністратор також може активувати обліковий запис у Налаштуваннях > Адміністрування > Керування користувачами.

### Гілка PKCE

Gramps Web вирішує, чи використовувати PKCE, коли починається вхід (див. [PKCE](#pkce)). Щоб дізнатися, що сталося у вашому налаштуванні, пройдіть через ці запитання в порядку:

1. **Чи встановлено `OIDC_PKCE`?** (Для вбудованих постачальників, `OIDC_GOOGLE_PKCE` або `OIDC_MICROSOFT_PKCE`.)
    - `True`: використовується PKCE. Перейдіть до питання 3.
    - `False`: PKCE навмисно вимкнено, і документ виявлення постачальника ігнорується. Якщо ваш постачальник вимагає PKCE, видаліть налаштування або встановіть його на `True`.
    - Не встановлено або порожнє: продовжуйте з питання 2.
2. **Чи містить документ виявлення `S256`?** Відкрийте `<issuer>/.well-known/openid-configuration` і шукайте `S256` у `code_challenge_methods_supported`.
    - Так: PKCE використовується автоматично. Продовжуйте з питання 3.
    - Ні, або поле відсутнє: PKCE **не** використовується. Встановіть `OIDC_PKCE` на `True`, якщо ваш постачальник його вимагає. Також перевірте журнал сервера на наявність `Could not check the provider for PKCE support`, що означає, що документ виявлення не вдалося отримати, і PKCE тому залишено вимкненим.
3. **Чи дійсно PKCE було надіслано?** Розпочніть вхід і подивіться на адресу сторінки входу постачальника (або перше перенаправлення у вкладці мережі вашого браузера). Вона повинна містити `code_challenge=` та `code_challenge_method=S256`.
    - Присутній, але вхід все ще зазнає невдачі на зворотному виклику: постачальник відхилив код перевірки. Куки сесії могли бути втрачені між перенаправленням та зворотним викликом (див. гілку 3 вище), або постачальник не підтримує `S256`, у такому випадку встановіть `OIDC_PKCE` на `False`, якщо постачальник не вимагає PKCE.
    - Відсутній: вище наведені налаштування не були застосовані. Перевірте, що змінна середовища має правильний префікс і значення малими літерами (наприклад, `GRAMPSWEB_OIDC_PKCE=true` у Docker; `True` не читається як логічне значення), перезапустіть сервер і знову перегляньте конфігурацію.

!!! note
    З увімкненим PKCE у постачальника як *необов'язковим* або зовсім не увімкненим, входи працюють незалежно від того, чи надсилає Gramps Web виклик. Лише постачальники (або клієнти), налаштовані на *вимогу* PKCE, роблять це налаштування важливим.

## Приклад конфігурацій

### Кастомний OIDC постачальник (Keycloak)

```python
TREE="Моє сімейне дерево"
BASE_URL="https://mytree.example.com"
SECRET_KEY="..."  # ваш секретний ключ
USER_DB_URI="sqlite:////path/to/users.sqlite"

# Кастомна OIDC конфігурація
OIDC_ENABLED=True
OIDC_ISSUER="https://auth.example.com/realms/myrealm"
OIDC_CLIENT_ID="gramps-web"
OIDC_CLIENT_SECRET="ваш-секрет-клієнта"
OIDC_NAME="Сімейний SSO"
OIDC_SCOPES="openid email profile"
OIDC_AUTO_REDIRECT=True  # Необов'язково: автоматично перенаправляти на SSO вхід
OIDC_DISABLE_LOCAL_AUTH=True  # Необов'язково: відключити вхід за допомогою імені користувача/пароля

# Необов'язково: Відображення ролей з OIDC груп на ролі Gramps
OIDC_ROLE_CLAIM="groups"  # або "roles" в залежності від вашого постачальника
OIDC_GROUP_ADMIN="gramps-admins"
OIDC_GROUP_EDITOR="gramps-editors"
OIDC_GROUP_MEMBER="gramps-members"

EMAIL_HOST="mail.example.com"
EMAIL_PORT=465
EMAIL_USE_SSL=True  # Використовувати імпліцитний SSL для порту 465
EMAIL_HOST_USER="gramps@example.com"
EMAIL_HOST_PASSWORD="..." # ваш SMTP пароль
DEFAULT_FROM_EMAIL="gramps@example.com"
```

### Pocket ID

Створіть OIDC клієнта в Pocket ID з URL-адресою перенаправлення `<BASE_URL>/api/oidc/callback/custom` (див. [Обов'язкові URL-адреси перенаправлення](#required-redirect-uris)). Якщо ви увімкнете "Вимагати PKCE" для клієнта, додаткова конфігурація Gramps Web не потрібна, оскільки Pocket ID рекламує підтримку PKCE у своєму документі виявлення. Потім налаштуйте:

```
GRAMPSWEB_OIDC_ENABLED=True
GRAMPSWEB_OIDC_ISSUER=https://id.example.com
GRAMPSWEB_OIDC_CLIENT_ID=<client id>
GRAMPSWEB_OIDC_CLIENT_SECRET=<client secret>
GRAMPSWEB_OIDC_NAME=Pocket ID
```

### Keycloak

Більшість конфігурацій для Keycloak можна залишити за замовчуванням (*Клієнт → Створити клієнта → Аутентифікація клієнта УВІМКНЕНА*).
Є кілька винятків:

1. **Обсяг OpenID** – Обсяг `openid` за замовчуванням не включений у всіх версіях Keycloak. Щоб уникнути проблем, додайте його вручну: *Клієнт → [Клієнт Gramps] → Клієнтські обсяги → Додати обсяг → Назва: `openid` → Встановити за замовчуванням.*
2. **Ролі** – Ролі можуть бути призначені або на рівні клієнта, або глобально для кожного царства.

    * Якщо ви використовуєте ролі клієнта, встановіть параметр конфігурації `OIDC_ROLE_CLAIM` на: `resource_access.[gramps-client-name].roles`
    * Щоб зробити ролі видимими для Gramps, перейдіть до *Клієнтські обсяги* (верхній рівень, не під конкретним клієнтом), потім: *Ролі → Мапери → ролі клієнта → Додати до userinfo → УВІМКНУТО.*
