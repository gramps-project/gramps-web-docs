# OIDC Аутентификация

Gramps Web поддерживает аутентификацию OpenID Connect (OIDC), позволяя пользователям входить в систему с использованием внешних поставщиков идентификации. Это включает встроенные поставщики Google и Microsoft, а также пользовательские OIDC поставщики, такие как Keycloak, Authentik и Authelia.

!!! warning "GitHub как OIDC поставщик больше не поддерживается"
    Если у вас установлены `OIDC_GITHUB_CLIENT_ID` / `OIDC_GITHUB_CLIENT_SECRET` из более ранней версии, удалите их – они теперь игнорируются, и пользователи, которые ранее входили через GitHub, больше не могут войти таким образом. GitHub является поставщиком OAuth 2.0, а не поставщиком OpenID Connect, и никогда не возвращал требование, на которое полагается Gramps Web для идентификации, поэтому он никогда не был полностью надежным.

## Обзор

Аутентификация OIDC позволяет вам:

- Использовать внешние поставщики идентификации для аутентификации пользователей
- Поддерживать несколько поставщиков аутентификации одновременно
- Соответствовать OIDC группам/ролям ролям пользователей Gramps Web
- Реализовать единую аутентификацию (SSO) и единую выход (Single Sign-Out)
- При желании отключить локальную аутентификацию по имени пользователя/паролю

## Конфигурация

Чтобы включить аутентификацию OIDC, вам необходимо настроить соответствующие параметры в вашем файле конфигурации Gramps Web или переменных окружения. См. страницу [Конфигурация сервера](configuration.md#settings-for-oidc-authentication) для полного списка доступных настроек OIDC.

!!! info
    При использовании переменных окружения не забудьте добавить префикс `GRAMPSWEB_` к каждому имени настройки (например, `GRAMPSWEB_OIDC_ENABLED`). См. [Файл конфигурации против переменных окружения](configuration.md#configuration-file-vs-environment-variables) для получения подробностей.

### Встроенные поставщики

Gramps Web имеет встроенную поддержку популярных поставщиков идентификации. Чтобы использовать их, вам нужно только указать идентификатор клиента и секрет клиента:

- **Google**: `OIDC_GOOGLE_CLIENT_ID` и `OIDC_GOOGLE_CLIENT_SECRET`
- **Microsoft**: `OIDC_MICROSOFT_CLIENT_ID` и `OIDC_MICROSOFT_CLIENT_SECRET`

Вы можете настроить несколько поставщиков одновременно. Система автоматически определит, какие поставщики доступны на основе значений конфигурации.

!!! tip "Microsoft: развертывания с одним арендатором"
    Встроенный поставщик Microsoft использует многоарендный `/common` конечный пункт и принимает входы из любого аккаунта Microsoft по умолчанию. Если вы хотите разрешить пользователям вход только из вашего собственного арендатора, используйте [пользовательского OIDC поставщика](#custom-oidc-providers) с вашим специфическим для арендатора URL-адресом эмитента, который сохраняет проверку эмитента активной и ограничивает входы только для этого арендатора.

### Пользовательские OIDC Поставщики

Для пользовательских OIDC поставщиков (таких как Keycloak, Authentik, Authelia или арендатор Microsoft Entra с одним арендатором) используйте следующие настройки:

Ключ | Описание
----|-------------
`OIDC_ENABLED` | Логическое значение, указывающее, следует ли включить аутентификацию OIDC. Установите в `True`.
`OIDC_ISSUER` | URL-адрес эмитента вашего поставщика. Открытие осуществляется из `<issuer>/.well-known/openid-configuration`.
`OIDC_CLIENT_ID` | Идентификатор клиента для вашего OIDC поставщика
`OIDC_CLIENT_SECRET` | Секрет клиента для вашего OIDC поставщика
`OIDC_NAME` | Пользовательское отображаемое имя (необязательно, по умолчанию "OIDC")
`OIDC_SCOPES` | OAuth области (необязательно, по умолчанию "openid email profile")
`OIDC_USERNAME_CLAIM` | Требование, используемое для генерации имени пользователя (необязательно, по умолчанию "preferred_username")
`OIDC_PKCE` | Использовать ли PKCE, см. [PKCE](#pkce) (необязательно, включается автоматически, если поставщик это поддерживает)

### PKCE

С версии Gramps Web API 3.23, Gramps Web поддерживает [PKCE](https://datatracker.ietf.org/doc/html/rfc7636) (Proof Key for Code Exchange, метод `S256`) для потока авторизационного кода. Некоторые поставщики идентификации, такие как Pocket ID, могут быть настроены на *требование* PKCE для клиента и отклонять входы, которые его не используют. Более ранние версии Gramps Web API никогда не использовали PKCE, поэтому входы с таким клиентом терпят неудачу.

Использование PKCE определяется при входе следующим образом:

- Если `OIDC_PKCE` установлено в `True`, используется PKCE.
- Если `OIDC_PKCE` установлено в `False`, PKCE не используется, даже если поставщик это поддерживает.
- Если `OIDC_PKCE` не установлено или установлено, но пусто, PKCE используется, если документ обнаружения поставщика (`/.well-known/openid-configuration`) содержит `S256` в `code_challenge_methods_supported`, и не используется в противном случае.

Для большинства настроек вам не нужно ничего устанавливать. Установите `OIDC_PKCE` в `True`, если ваш поставщик требует PKCE, но не рекламирует `S256` в своем документе обнаружения, и в `False`, если ваш поставщик рекламирует `S256`, но неправильно с ним работает. В качестве переменных окружения логические значения должны быть в нижнем регистре (`GRAMPSWEB_OIDC_PKCE=true`), см. [Конфигурация](configuration.md).

Для встроенных поставщиков соответствующие параметры – это `OIDC_GOOGLE_PKCE` и `OIDC_MICROSOFT_PKCE`.

Код проверщика PKCE хранится в сессии пользователя между перенаправлением к поставщику и обратным вызовом, поэтому это не требует изменений в URI перенаправления.

### Многоуровневые настройки

На сервере с несколькими деревьями пользователь, который входит с идентичностью, уже связанной с аккаунтом Gramps Web, входит в дерево этого аккаунта, поэтому обычная страница входа работает для них.

Чтобы создать *новый* аккаунт с идентичностью OIDC, Gramps Web необходимо знать, к какому дереву он должен принадлежать. Поэтому новые пользователи должны начинать с ссылки регистрации дерева (`/register/<tree_id>`, см. [Ссылка регистрации](../administration/users.md#registration-link-multi-tree-setup-only)) или со страницы входа дерева (`/login/<tree_id>`). Оба предлагают настроенные поставщики. Вход с неизвестной идентичностью с обычной страницы входа отклоняется с сообщением, указывающим на ссылку регистрации. Это требует Gramps Web API 3.25.3 и Gramps Web 26.11.2 или новее.

За кулисами вход начинается с:

```
GET /api/oidc/login/?provider=<id>&tree=<tree_id>
```

где `tree` является необязательным, если создается новый аккаунт. Передача ID дерева, которого не существует, приводит к неудаче входа. На сервере с одним деревом `tree` является необязательным, но если он указан, он должен соответствовать настроенному `TREE`.

Идентичность OIDC привязана к ровно одному аккаунту Gramps Web, который, в свою очередь, принадлежит ровно одному дереву – вход в другое дерево завершается неудачей, а не перемещением аккаунта. Нет способа связать одну идентичность у поставщика с аккаунтами в нескольких деревьях; пользователи, которым нужен доступ к нескольким деревьям, должны иметь отдельные идентичности у поставщика (например, разные имена пользователей или аккаунты).

!!! warning
    Учетная запись администратора сайта без связанного дерева (см. [создание учетной записи администратора](../administration/owner.md)) не может быть создана через OIDC, поскольку учетная запись, созданная с помощью входа OIDC, всегда принадлежит дереву. Создавайте такие учетные записи с помощью локального имени пользователя и пароля.

### Нативные приложения

Нативные приложения, такие как мобильные приложения для Gramps Web, могут позволить пользователю войти в систему в системном браузере и получить результат по ссылке `https` приложения. С версии Gramps Web API 3.26 это работает, если ссылка указана в `OIDC_ALLOWED_REDIRECT_URIS`, например:

```
GRAMPSWEB_OIDC_ALLOWED_REDIRECT_URIS='["https://app.example.com/oidc-callback"]'
```

Документация приложения подскажет, какую ссылку добавить. Зарегистрированные URI перенаправления у поставщика идентификации остаются прежними.

## Обязательные URI перенаправления

При настройке вашего OIDC поставщика вы должны зарегистрировать следующий URI перенаправления:

**Для OIDC поставщиков, которые поддерживают подстановочные знаки: (например, Authentik)**

- `https://your-gramps-backend.com/api/oidc/callback/*`

Где `*` является подстановочным знаком regex. В зависимости от интерпретатора regex вашего поставщика это также может быть `.*` или аналогично. Убедитесь, что regex включен, если ваш поставщик это требует (например, Authentik).

**Для OIDC поставщиков, которые не поддерживают подстановочные знаки: (например, Authelia)**

- `https://your-gramps-backend.com/api/oidc/callback/custom`

Дерево никогда не является частью URI перенаправления, даже на серверах с несколькими деревьями – оно передается отдельно в сессии, поскольку поставщики требуют, чтобы URI перенаправления точно соответствовал зарегистрированному.

## Соответствие ролям

Gramps Web может автоматически сопоставлять группы или роли OIDC от вашего поставщика идентификации с ролями пользователей Gramps Web. Это позволяет вам централизованно управлять разрешениями пользователей в вашем поставщике идентификации. Соответствие ролям работает одинаково для всех поставщиков, встроенных или пользовательских.

### Конфигурация

Используйте эти настройки для конфигурации соответствия ролям:

Ключ | Описание
----|-------------
`OIDC_ROLE_CLAIM` | Имя требования в OIDC токене, которое содержит группы/роли пользователя. По умолчанию "groups". Поддерживаются точечные пути, например `realm_access.roles`.
`OIDC_GROUP_ADMIN` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Admin" в Gramps
`OIDC_GROUP_OWNER` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Owner" в Gramps
`OIDC_GROUP_EDITOR` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Editor" в Gramps
`OIDC_GROUP_CONTRIBUTOR` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Contributor" в Gramps
`OIDC_GROUP_MEMBER` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Member" в Gramps
`OIDC_GROUP_GUEST` | Имя группы/роли от вашего OIDC поставщика, которое соответствует роли "Guest" в Gramps

### Поведение соответствия ролям

Если ни одна настройка `OIDC_GROUP_*` не настроена, соответствие ролям отключено, и роли управляются вручную в Gramps Web; новые OIDC аккаунты создаются отключенными и должны быть одобрены существующим владельцем или администратором (см. [Первый вход и начальная настройка](#first-login-and-bootstrapping) ниже).

После настройки соответствия ролям при каждом входе:

- Если требование роли присутствует и пользователь принадлежит к сопоставленной группе, ему присваивается соответствующая роль.
- Если требование роли присутствует, но пользователь не принадлежит ни к одной сопоставленной группе, его роль устанавливается как отключенная. Это значение по умолчанию с закрытым отказом, а не ошибка – Gramps Web не может вывести роль для группы, которую он не распознает.
- Если требование роли полностью отсутствует в токене, существующая роль остается без изменений; новый аккаунт по-прежнему по умолчанию отключен.

!!! warning "Google не отправляет требование групп"
    Токены Google никогда не включают требование `groups`, поэтому при включенном соответствии ролям входы Google попадают под "требование отсутствует" выше: существующие пользователи сохраняют свою роль, но новые пользователи Google создаются отключенными и нуждаются в ручном одобрении. Имейте это в виду, прежде чем включать соответствие ролям только для другого поставщика – это не отключает существующих пользователей Google.

Microsoft Entra возвращает роли приложений и членства в группах только в ID токене, а не из конечной точки userinfo. Gramps Web объединяет требования ID токена в ответ userinfo, чтобы `OIDC_ROLE_CLAIM` работал так же, как и для других поставщиков; где оба содержат требование, значение userinfo имеет приоритет.

## Первый вход и начальная настройка

Новые аккаунты, созданные через OIDC, начинают с отключенным состоянием, если соответствие ролям не назначает им роль (см. выше). В совершенно новом экземпляре никто не может одобрить отключенный аккаунт, и если `OIDC_DISABLE_LOCAL_AUTH` также включен, нет возможности входа по паролю.

!!! warning "Настройте группу владельцев/администраторов перед первым входом"
    Прежде чем кто-либо войдет через OIDC в первый раз, установите `OIDC_GROUP_OWNER` (или `OIDC_GROUP_ADMIN`) и убедитесь, что первый пользователь принадлежит к этой группе у поставщика. В противном случае экземпляр не может быть начат через OIDC вообще.

## Аккаунты и имена пользователей

Аккаунты, созданные через OIDC, получают сгенерированное имя пользователя, назначаемое один раз при создании аккаунта и никогда не изменяемое при последующих входах:

- Встроенные поставщики: `<provider>_<claim value>`, например `microsoft_alice@contoso.com`
- Пользовательский поставщик: чистое значение требования, например `alice`

Числовой суффикс добавляется при коллизии. Нет способа переименовать имя пользователя аккаунта, созданного через OIDC, впоследствии; полное имя и адрес электронной почты, напротив, обновляются при каждом входе.

Вход OIDC никогда не прикрепляется к существующему локальному аккаунту, который случайно разделяет свой адрес электронной почты – это сделано намеренно, поскольку связывание аккаунтов по электронной почте является вектором захвата аккаунта. Пользователь, который уже имеет локальный аккаунт, получает второй, отдельный аккаунт в первый раз, когда он входит через OIDC, если он сначала не свяжет поставщика со своим аккаунтом.

С версии Gramps Web API 3.24 пользователи могут связывать идентичности OIDC со своими существующими аккаунтами и перечислять и разъединять их в разделе [Настройки пользователя > Связанные методы входа](../user-guide/settings.md#linked-sign-in-methods). Связывание требует недавнего входа и подтверждается собственным токеном пользователя, поэтому оно также работает, когда фронтенд находится на другом источнике, чем API. Идентичность может принадлежать только одному аккаунту; чтобы связать ту, которая уже имеет свой собственный аккаунт, администратор сначала удаляет этот аккаунт (его изменения остаются, но история ревизий больше не показывает его имя). Последнюю связанную идентичность можно разъединить только с текущим паролем аккаунта и не может быть разъединена вообще, если установлено `OIDC_DISABLE_LOCAL_AUTH`.

Адреса электронной почты от поставщика хранятся только в том случае, если поставщик помечает их как проверенные (или полностью опускает требование `email_verified`); в противном случае вход продолжается без хранения адреса электронной почты. Поскольку адреса электронной почты не обязательно должны быть уникальными (с версии Gramps Web API 3.22), адрес хранится, даже если другой аккаунт уже его использует.

## Выход OIDC

Gramps Web поддерживает единую выход (SSO logout) для OIDC поставщиков. `GET /api/oidc/logout/` ищет `end_session_endpoint` поставщика и возвращает его как `logout_url` в ответе; именно фронтенд Gramps Web направляет браузер туда, чтобы фактически завершить сессию у поставщика идентификации. `logout_url` равен `null`, когда у поставщика нет `end_session_endpoint`.

!!! warning "Токены не аннулируются при выходе"
    Выход завершает только сессию браузера; в настоящее время нет способа аннулировать токен Gramps Web, который уже был выдан. Токены остаются действительными до истечения срока действия (`JWT_ACCESS_TOKEN_EXPIRES`, по умолчанию 15 минут для токенов доступа), независимо от того, вышел ли пользователь с Gramps Web или у поставщика идентификации.

## Устранение неполадок

Начните с точки, где вход останавливается, и следуйте по ветке. Gramps Web записывает причину неудачного обратного вызова (ищите `OIDC callback error for provider` в журнале сервера), которая обычно более конкретна, чем сообщение, отображаемое в браузере.

**1. Не хватает кнопки входа?**

- Проверьте `<BASE_URL>/api/oidc/config/`. Если `enabled` равно `false` или `providers` пусто, OIDC не настроен: `OIDC_ENABLED` должен быть `True`, а пользовательский поставщик должен иметь как `OIDC_ISSUER`, так и `OIDC_CLIENT_ID`.
- Встроенный поставщик (Google, Microsoft) регистрируется только в том случае, если установлены как его идентификатор клиента, так и его секрет клиента.
- Посмотрите в журнал сервера при запуске на `Could not load discovery document`. Это означает, что сервер не смог достичь `<issuer>/.well-known/openid-configuration` (или `OIDC_OPENID_CONFIG_URL`). Он повторяет попытку при первом использовании, но контейнер Gramps Web должен быть в состоянии разрешить и достичь URL-адрес эмитента самостоятельно, а не только ваш браузер.

**2. Получает ли браузер ошибку сразу после отправки к поставщику?**

Ошибка отображается поставщиком идентификации до того, как вы войдете.

- *"несоответствие URI перенаправления"* (или аналогично): URI перенаправления, зарегистрированный у поставщика, должен точно соответствовать, включая схему, хост, порт и идентификатор поставщика. См. [Обязательные URI перенаправления](#required-redirect-uris). Обратите внимание, что он строится из `BASE_URL`, поэтому неправильный `BASE_URL` дает неправильный URI перенаправления.
- *Ошибка PKCE* (например, `invalid_request`, "требуется код вызова" или отсутствующий параметр `code_challenge`): поставщик требует PKCE, но Gramps Web его не отправил. Перейдите к [ветке PKCE](#pkce-branch) ниже.

**3. Поставщик принимает вход, но Gramps Web затем показывает ошибку?**

- *`mismatching_state`, или ошибка упоминает сессию или состояние*: браузер не отправил обратно cookie сессии, который Gramps Web установил, когда вход начался. Этот cookie также содержит проверщик кода PKCE. Убедитесь, что адрес в браузере соответствует `BASE_URL` (одинаковая схема и хост), что обратный прокси передает cookie и оригинальный хост, и что вход начинается и завершается в одной и той же вкладке или окне браузера.
- *`OIDC authentication failed for <provider>` (HTTP 401)*: проверьте журнал сервера на основную причину. Общие причины – это неправильный секрет клиента, URL-адрес эмитента, который не соответствует требованию `iss` токенов, и поставщик, возвращающий ошибку в обратный вызов (например, PKCE, см. ниже).
- *Слишком много попыток*: конечные точки входа и обратного вызова имеют ограничение по количеству запросов (5 запросов в минуту). Подождите минуту и повторите попытку.

**4. Вход проходит успешно, но вы видите "Аккаунт на рассмотрении" или не можете ничего сделать?**

Новые аккаунты создаются отключенными, если соответствие ролям не назначает роль. См. [Первый вход и начальная настройка](#first-login-and-bootstrapping) и [Поведение соответствия ролям](#role-mapping-behavior). Администратор также может активировать аккаунт в разделе Настройки > Администрирование > Управление пользователями.

### Ветка PKCE

Gramps Web решает, использовать ли PKCE, когда начинается вход (см. [PKCE](#pkce)). Чтобы выяснить, что произошло в вашей настройке, пройдите через эти вопросы в порядке:

1. **Установлено ли `OIDC_PKCE`?** (Для встроенных поставщиков, `OIDC_GOOGLE_PKCE` или `OIDC_MICROSOFT_PKCE`.)
    - `True`: используется PKCE. Перейдите к вопросу 3.
    - `False`: PKCE намеренно отключен, и документ обнаружения поставщика игнорируется. Если ваш поставщик требует PKCE, удалите настройку или установите ее в `True`.
    - Не установлено или пусто: продолжайте с вопроса 2.
2. **Указывает ли документ обнаружения на `S256`?** Откройте `<issuer>/.well-known/openid-configuration` и ищите `S256` в `code_challenge_methods_supported`.
    - Да: PKCE используется автоматически. Продолжайте с вопроса 3.
    - Нет, или поле отсутствует: PKCE **не** используется. Установите `OIDC_PKCE` в `True`, если ваш поставщик требует этого. Также проверьте журнал сервера на `Could not check the provider for PKCE support`, что означает, что документ обнаружения не удалось получить, и PKCE был, следовательно, отключен.
3. **Действительно ли PKCE был отправлен?** Начните вход и посмотрите на адрес страницы входа поставщика (или первое перенаправление в сетевой вкладке вашего браузера). Он должен содержать `code_challenge=` и `code_challenge_method=S256`.
    - Присутствует, но вход все равно не проходит на обратном вызове: поставщик отклонил проверщик кода. Cookie сессии могли быть потеряны между перенаправлением и обратным вызовом (см. ветку 3 выше), или поставщик не поддерживает `S256`, в этом случае установите `OIDC_PKCE` в `False`, если поставщик не требует PKCE.
    - Отсутствует: вышеуказанные настройки не были применены. Проверьте, что переменная окружения имеет правильный префикс и значение в нижнем регистре (например, `GRAMPSWEB_OIDC_PKCE=true` в Docker; `True` не читается как логическое значение), перезапустите сервер и снова посмотрите на конфигурацию.

!!! note
    При включенном PKCE у поставщика как *необязательном* или вообще не включенном, входы работают независимо от того, отправляет ли Gramps Web вызов. Только поставщики (или клиенты), настроенные на *требование* PKCE, делают это значение важным.

## Примеры конфигураций

### Пользовательский OIDC Поставщик (Keycloak)

```python
TREE="Мое семейное дерево"
BASE_URL="https://mytree.example.com"
SECRET_KEY="..."  # ваш секретный ключ
USER_DB_URI="sqlite:////path/to/users.sqlite"

# Пользовательская конфигурация OIDC
OIDC_ENABLED=True
OIDC_ISSUER="https://auth.example.com/realms/myrealm"
OIDC_CLIENT_ID="gramps-web"
OIDC_CLIENT_SECRET="your-client-secret"
OIDC_NAME="Семейный SSO"
OIDC_SCOPES="openid email profile"
OIDC_AUTO_REDIRECT=True  # Необязательно: автоматически перенаправлять на SSO вход
OIDC_DISABLE_LOCAL_AUTH=True  # Необязательно: отключить вход по имени пользователя/паролю

# Необязательно: соответствие ролям от групп OIDC к ролям Gramps
OIDC_ROLE_CLAIM="groups"  # или "roles" в зависимости от вашего поставщика
OIDC_GROUP_ADMIN="gramps-admins"
OIDC_GROUP_EDITOR="gramps-editors"
OIDC_GROUP_MEMBER="gramps-members"

EMAIL_HOST="mail.example.com"
EMAIL_PORT=465
EMAIL_USE_SSL=True  # Использовать неявный SSL для порта 465
EMAIL_HOST_USER="gramps@example.com"
EMAIL_HOST_PASSWORD="..." # ваш SMTP пароль
DEFAULT_FROM_EMAIL="gramps@example.com"
```

### Встроенный Поставщик (Google)

```python
TREE="Мое семейное дерево"

```

### Несколько Поставщиков

Вы можете одновременно включить несколько OIDC поставщиков:

```python
TREE="Мое семейное дерево"
BASE_URL="https://mytree.example.com"
SECRET_KEY="..."  # ваш секретный ключ
USER_DB_URI="sqlite:////path/to/users.sqlite"

# Пользовательский поставщик

# Google OAuth
OIDC_GOOGLE_CLIENT_ID="your-google-client-id"
OIDC_GOOGLE_CLIENT_SECRET="your-google-client-secret"

# Microsoft OAuth
OIDC_MICROSOFT_CLIENT_ID="your-microsoft-client-id"
OIDC_MICROSOFT_CLIENT_SECRET="your-microsoft-client-secret"
```

### Pocket ID

Создайте OIDC клиента в Pocket ID с URI перенаправления `<BASE_URL>/api/oidc/callback/custom` (см. [Обязательные URI перенаправления](#required-redirect-uris)). Если вы включите "Требовать PKCE" для клиента, дополнительная конфигурация Gramps Web не требуется, поскольку Pocket ID рекламирует поддержку PKCE в своем документе обнаружения. Затем настройте:

```
GRAMPSWEB_OIDC_ENABLED=True
GRAMPSWEB_OIDC_ISSUER=https://id.example.com
GRAMPSWEB_OIDC_CLIENT_ID=<client id>
GRAMPSWEB_OIDC_CLIENT_SECRET=<client secret>
GRAMPSWEB_OIDC_NAME=Pocket ID
```

### Keycloak

Большую часть конфигурации для Keycloak можно оставить по умолчанию (*Клиент → Создать клиента → Аутентификация клиента ВКЛ*).
Есть несколько исключений:

1. **Область OpenID** – Область `openid` не включена по умолчанию во всех версиях Keycloak. Чтобы избежать проблем, добавьте ее вручную: *Клиент → [Клиент Gramps] → Области клиентов → Добавить область → Имя: `openid` → Установить по умолчанию.*
2. **Роли** – Роли могут быть назначены либо на уровне клиента, либо глобально для каждого реалма.

    * Если вы используете клиентские роли, установите параметр конфигурации `OIDC_ROLE_CLAIM` на: `resource_access.[gramps-client-name].roles`
    * Чтобы сделать роли видимыми для Gramps, перейдите в *Области клиентов* (верхний уровень, а не под конкретным клиентом), затем: *Роли → Мапперы → клиентские роли → Добавить в userinfo → ВКЛ.*
